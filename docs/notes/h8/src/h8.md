# h8

During a recent incident response engagement, I came across a ransomware variant which enctrypted disk images directly from the hypervisor.
This environment had no centralized logging. It was thereby necessary to evaluate the encrypted state of the machines in order to potentially (1) extract lost data, and (2) to extract forensic artifacts for later analysis.
My theory here was that since it would be prohibitively slow to encrypt all virtual machine files fully, the encryptor would target fixed sections of the file and only encrypt those, resulting in a partial encryption allowing recovery of unencrypted data from the unaffected regions.
In order to assess if this was the case, and if subsequent recovery efforts were warranted, one first needs to get a clear picture of the encrypted files themselves to gague throgoughness of the encryption process.

> NOTE: High entropy sections need not be encrypted. Compression, random padding etc can produce high entropy sections as well.

While commercial tools like `X-Ways` can do this, I couldnt find a open source tool that achieve this specific goal.
Therefore, I decided to write my own, since im currently in the process of wanting to learn more `Go`.

First, however, one needs a mechanism to identify encrypted secions. I decided on using `Shannon Entropy`.

## Shannon Entropy

Shannon entropy can be understood as the `expected level of surprise one obtains from learning of a particular outcome`. 
"Surprise" has an inverse relationship with probability: if something is highly improbably, my surprise of observing it is high.
As such, one can compute surprise as follows:

```math
S(X) = \log_2{\frac{1}{p(x)}}
```

Note we take the log of the inverse, as the information content of independent events should be additive. Omitting the logarithm would make the result multiplicative.
Now, borrowing from the concept of expected values, we can translate the surprise `S(X)` into the expected surprise, which would be the shannon entropy. This can be done as follows:

```math
H(X) = \sum_{i=1}^n S(x_i)P(X=x_i)
```

where `i` is the `ith` iteration of discrete random variable `X`, and $$P(X=x_i)$$ is the probability of observing that value.
Note we take the log with a base of two such that information is measured in bits.
Plugging in the equation for `S(X)` we get:


```math
H(X) = \sum_{i=1}^n \log_2{\frac{1}{p(x_i)}} P(X=x_i)
```

which simplifies to:

```math
H(X) = -\sum_{i=1}^n {p(x_i)} \log_2{p(x_i)}
```

## H8

[`H8`](https://github.com/manfred6/h8) gives two options as for the unit of measurement the entropy is calculated for. One can compute either `bitwise` or `bytewise` Shannon entropy using the `--bit` or `--byte` flags respectively.
Bitwise entropy measures the "balance" between zero and one bits within each window. A value approaching 1 bit/bit indicates an approximately even distribution, while a value approaching 0 indicates that one bit value dominates. Since this measurement does not consider the ordering of bits, structured data (for example `10101010 10101010`) with an even zero/one distribution may also produce high bitwise entropy.
Bytewise entropy preserves more information about the underlying data (each unit of measurement has $$2^8 = 256$$ possible values), rather than just collapsing everything into bits ($$2^1 = 2$$ possible values), yielding higher fidelity signal.

These functions are implemented [`here`](https://github.com/manfred6/h8/blob/main/cmd/root.go).
My `bitwise` implementation looks as follows:
```go
func bitEntropy(buf []byte) float64 {
	var pX1, sP1, pX0, sP0 float64
	var totalOneBits int
	var bufSize int = len(buf) * 8

	for _, i := range buf {
		totalOneBits += bits.OnesCount8(i)
	}

	pX1 = float64(totalOneBits) / float64(bufSize)
	pX0 = float64(bufSize-totalOneBits) / float64(bufSize)

	if pX1 > 0 {
		sP1 = math.Log2(1 / pX1)
	}
	if pX0 > 0 {
		sP0 = math.Log2(1 / pX0)
	}
	return pX1*sP1 + pX0*sP0
}
```

while the `bytewise` functions is implemented as:
```go
func byteEntropy(buf []byte) float64 {
	var counts []int64 = make([]int64, 256)
	var e float64
	for _, byte := range buf {
		counts[byte]++
	}

	for i := range counts {
		var s, p float64
		p = float64(counts[i]) / float64(len(buf))
		if p > 0 {
			s = math.Log2(1 / p)
			e += p * s
		}
	}
	return e
}
```

These can surely be optimized, but they perform fine for my usecase.

```bash
./h8 ./disk.raw --byte
```
